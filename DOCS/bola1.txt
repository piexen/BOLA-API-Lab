BOLA 1 — MediNotes
======================================================================

Что это такое
----------------------------------------------------------------------

BOLA (Broken Object Level Authorization) — дыра в авторизации на уровне
объекта. Другое имя той же ошибки: IDOR (Insecure Direct Object Reference).

Суть: вы уже вошли в систему (есть логин, пароль, Bearer-токен). Сервер
знает, кто вы. Но когда вы просите конкретный объект — запись 104,
пациента 4, рецепт 302 — он не проверяет, ваш ли это объект. Достаточно
знать id.

Это не «взлом без пароля». Это «я пациент Козлов, а читаю карту Сидорова,
потому что в URL подставил чужой id».

Типичная картина в этой лабе:

  GET /notes          — список фильтруется, видны только свои записи
  GET /notes/104      — по id отдаётся любая запись, без проверки владельца

Список выглядит безопасно. Прямой доступ к объекту — нет.
Это и есть классический BOLA: list vs item.


Что вы делаете в лабе
----------------------------------------------------------------------

MediNotes — учебный REST API клиники. Медицинские записи, приёмы, рецепты.
Аутентификация есть. Проверки «этот объект принадлежит текущему
пользователю» на большинстве эндпоинтов нет.

Сайт лабы:     http://localhost:3847/bola
API:           http://localhost:3847/bola/api/v1
Swagger:       http://localhost:3847/bola/docs

Пароль входа на страницу лабы и в API: portfolio-demo-only
(его же выдаёт преподаватель, если стенд закрыт формой)

Работать нужно от имени patient.kozlov, если в задании не сказано иначе.


Как начать
----------------------------------------------------------------------

1. Откройте http://localhost:3847/bola (пароль страницы: portfolio-demo-only).
2. Откройте Swagger: http://localhost:3847/bola/docs
3. Вызовите POST /auth/login:

     {
       "username": "patient.kozlov",
       "password": "portfolio-demo-only"
     }

4. Скопируйте accessToken из ответа.
5. Нажмите Authorize → вставьте: Bearer <accessToken>
   (слово Bearer и пробел обязательны, либо вставьте только токен,
   если Swagger сам добавляет Bearer).
6. Дальше все задания — Try it out в Swagger или curl.

Тот же login через curl:

  curl -s -X POST http://localhost:3847/bola/api/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username":"patient.kozlov","password":"portfolio-demo-only"}'

Во всех остальных запросах:

  Authorization: Bearer <accessToken>

Не путайте три разных секрета:

  portfolio-demo-only              — пароль лаборатории (страница + POST /auth/login)
  accessToken из login   — его ставите в Bearer; выглядит как mn_3_...
  DEMO_ONLY_03      — старый демо-ключ на странице; это не токен из login.
                           Им можно, но не нужно: нормальный путь — login.

Без Bearer защищённые эндпоинты отвечают 401. Это нормально:
аутентификация работает. Ломается именно авторизация на объект.


Пользователи
----------------------------------------------------------------------

  username           роль      id
  patient.kozlov     patient   3     ← вы
  patient.sidorov    patient   4     ← чужой пациент, его карта — цель
  dr.ivanov          doctor    1
  dr.petrova         doctor    2
  admin              admin     5

Флаг лабы: FLAG{BOLA_MEDICAL_RECORDS_LEAKED}
Он лежит в content записи notes/104 (карта Сидорова). Искать в JSON API,
не на HTML-странице /bola.


Как думать над каждым заданием
----------------------------------------------------------------------

1. Сначала вызовите «безопасный» список (свои данные).
2. Потом подставьте чужой id в тот же тип ресурса.
3. Сравните: список не показал объект, прямой запрос — показал.
4. Запишите: эндпоинт, параметр, код ответа, что утекло, тип BOLA
   (read / write), как чинить (проверка patientId / doctorId на сервере).


Задание 1. Вход и профиль
----------------------------------------------------------------------

Цель: понять, кто вы в API и чем пароль лабы отличается от токена.

  POST /auth/login
  GET  /users/me

Ожидание:
  login возвращает accessToken;
  /users/me → id=3, role=patient, username=patient.kozlov

portfolio-demo-only — пароль для login (один на всю лабу + username).
accessToken — сессия для остальных запросов. Без него /users/me = 401.


Задание 2. Свои записи vs чужая по id
----------------------------------------------------------------------

  GET /notes
  GET /notes/104

Ожидание:
  GET /notes → count=2, id 101 и 102 (только Козлов, patientId=3).
  GET /notes/104 → 200, запись Сидорова (patientId=4).

Почему 104 нет в списке, но открывается по id:
  список фильтрует по роли (patient видит только свои patientId).
  GET по id владельца не проверяет — классический BOLA на item.

Тип: read BOLA на объект, не на список.


Задание 3. Флаг
----------------------------------------------------------------------

  GET /notes/104

В поле content:
  FLAG{BOLA_MEDICAL_RECORDS_LEAKED}

Флаг только в JSON ответа API (Swagger / curl / Postman).
Страница /bola — справка, данные отдаёт REST.

Риск в реальной медсистеме: утечка чужой карты при знании или переборе id.


Задание 4. Список пациентов
----------------------------------------------------------------------

  GET /patients

Ожидание: Козлов (id=3) и Сидоров (id=4).

Пациент не должен видеть других пациентов клиники.
Это BOLA на коллекции (enumeration): разведка id для следующих запросов.


Задание 5. Все записи Сидорова
----------------------------------------------------------------------

  GET /patients/4/notes

Ожидание: notes 103 и 104, patientId=4.

Отличие от GET /notes/104: тот же доступ, но вложенный ресурс —
одним запросом все записи чужого пациента.

Исправление: перед выдачей проверять
  req.user.id === patientId
  (или врач привязан к этому пациенту).


Задание 6. Полное досье (export)
----------------------------------------------------------------------

  GET /patients/4/export

Ожидание: patient Сидоров + notes 103/104 + appointment 202 +
prescription 302.

Опаснее одиночного GET /notes/104: один запрос сливает все связанные
объекты (horizontal privilege escalation).


Задание 7. Write BOLA — изменить чужую запись
----------------------------------------------------------------------

  PUT /notes/103
  {
    "title": "Взломано BOLA",
    "content": "Изменено patient.kozlov"
  }

Ожидание: 200, запись 103 (patientId=4) изменена.

Это write BOLA: не чтение, а порча чужих медицинских данных.
Исправление: перед PUT проверять владельца (patientId / doctorId)
или роль admin с аудитом.

После опытов нажмите «Сбросить API» на /bola.


Задание 8. POST с чужим patientId
----------------------------------------------------------------------

  POST /notes
  {
    "title": "Фальшивая запись",
    "content": "Создано на чужого пациента",
    "patientId": 4
  }

Ожидание: 201, новая запись с patientId=4.

Сервер берёт patientId из тела и не сверяет с req.user.id.
Это атака на целостность: подмена/создание карты на другого человека.


Задание 9. IDOR на приёме и рецепте
----------------------------------------------------------------------

  GET /appointments/202
  GET /prescriptions/302

Ожидание:
  приём 202 → patientId=4, кабинет 7
  рецепт 302 → patientId=4, Аторвастатин 20 мг

Это отдельные сущности (не notes). IDOR нужно проверять на каждом
типе ресурса. Id можно взять из export (задание 6) или перебором.


Задание 10. DELETE чужой записи (по желанию)
----------------------------------------------------------------------

  DELETE /notes/103

Ожидание: запись Сидорова удалена. Это write BOLA на удаление.

DELETE /notes/101 от kozlov — своя запись, это уже не BOLA.
После демо: кнопка сброса на /bola.


Шпаргалка curl (подставьте TOKEN)
----------------------------------------------------------------------

  curl -s http://localhost:3847/bola/api/v1/notes \
    -H "Authorization: Bearer TOKEN"

  curl -s http://localhost:3847/bola/api/v1/notes/104 \
    -H "Authorization: Bearer TOKEN"

  curl -s http://localhost:3847/bola/api/v1/patients \
    -H "Authorization: Bearer TOKEN"

  curl -s http://localhost:3847/bola/api/v1/patients/4/export \
    -H "Authorization: Bearer TOKEN"


Как чинить BOLA в целом
----------------------------------------------------------------------

На каждом запросе к объекту сервер должен решить:

  этот объект принадлежит текущему пользователю
  ИЛИ у него есть явная роль/связь (лечащий врач, admin)

Нельзя доверять id из URL, query или body. Id — указатель, не право.
Право проверяется на сервере по данным из сессии/токена.
